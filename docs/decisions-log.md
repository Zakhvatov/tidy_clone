# Журнал решений координатора

Решения, принятые автономно (пользователь был недоступен для ответов). Правило самому себе:
выбирать наименее рискованный обратимый вариант, ничего не тратить и не удалять необратимо,
и оставлять здесь след для финального аудита.

## D1 · Pages-проект создаётся с `--force` (T1)

Новый wrangler делегирует `pages project create` в Workers и без `--force` падает на
«Could not detect a directory containing static files». Создание проекта с `--force` выполнено один
раз; последующие `pages deploy` идут обычным путём, `--force` больше не нужен.
Обратимо: проект можно удалить, приложение — статика.

## D2 · Саб-агенты запускаются через `pi -p`, а не через `claude` (flow-setup)

`claude` CLI установлен, но не залогинен («Not logged in · Please run /login»), а вход требует
интерактивной авторизации, которой в автономном режиме нет. `pi -p --no-session` работает headless,
умеет инструменты и уже авторизован (тот же провайдер, что у сессии). Orca-worktree остаются
доступны, но не потребовались: задачи резались по непересекающимся каталогам.

## D3 · Vision-провайдер требует заголовок `x-opencode-session` (T3)

`https://opencode.ai/zen/go/v1/chat/completions` без заголовка `x-opencode-session` отвечает
400 `MissingSessionID`; с заголовком (значение — любой UUID, провайдер использует его для
маршрутизации диалога) — 200. Проверено вживую: 6.2 с на реальной картинке 1024×1024.
В воркер добавлен `OpenCodeSessionId` на каждый запрос. Так же делает pi (`withOpenCodeSessionHeader`).
ADR-0003 не пересматривается: провайдер тот же, добавлена обязательная деталь протокола.

## D4 · Зависание `/classify` — не дефект воркера, а локальная сеть

Симптом: `POST /classify` с телом ~25 КБ обрывается через ~18–20 с (`curl: (56) Recv failure`).
Разбор:
- `wrangler tail` во время запроса не показал **ни одного события** — запрос не доходит до Cloudflare;
- граница воспроизводится: 4 КБ / 8 КБ / 12 КБ → ответ за 0.07–1.7 с, 16 КБ → таймаут, 20 КБ → обрыв;
- то же самое с `text/plain` без base64 → значит дело в размере тела, а не в содержимом;
- с edge (`tidy-probe2`) `opencode.ai` отвечает 200 за 202 мс, а chat/completions с неверным ключом —
  401 за 509 мс, то есть сеть Cloudflare до провайдера здорова.

Вывод: тело больше ~16 КБ режет **локальная сеть разработчика** — тот же класс проблемы, что описан
в README (Cisco AnyConnect Socket Filter). Это ограничение тестового окружения, а не приложения.
Следствие для проверок: живые проверки с большими телами делать нельзя с этой машины; проверять
через прямые запросы меньшего размера и через edge. Занесено в риск T21.

## D5 · Проверка прод-URL и воркера — через edge, а не из локальной сети (T1, T3)

Локально `*.pages.dev` не проходит TLS (DNS возвращает NXDOMAIN через локальный резолвер, при этом
через DoH записи есть: 172.66.45.7 / 172.66.46.249), а тела >16 КБ теряются. Поэтому живость
проверяется одноразовыми воркерами-пробами на edge Cloudflare (`tidy-probe`, `tidy-probe2`), которые
после проверки удаляются. Ограничение: воркер не может звать другой воркер того же аккаунта
(`error code: 1042`), поэтому проба страниц и проба провайдера — разные пробы.

## D6 · Дневной лимит нейронов Workers AI исчерпан — живой прогон генерации отложен

`POST /generate` начал отвечать 502. Причина найдена через `wrangler tail` (не догадка):

```
[tidy-api] generate model error: 4006: you have used up your daily free allocation of
10,000 neurons, please upgrade to Cloudflare's Workers Paid plan if you would like to continue usage.
```

Это исчерпание бесплатной дневной квоты Workers AI (10 000 нейронов, ADR-0003), а не дефект кода.
Кто израсходовал: живые проверки hardening'а (серия из 25 запросов на rate limit) и, главным образом,
прогон T11 — его retry-цикл слал запросы, каждый из которых **всё равно выполнял генерацию на сервере**,
даже если клиент не дожидался ответа (локальная сеть обрывает загрузку больших тел, D4).

Решения:
- Живой прогон T11 по 8 категориям **отложен до сброса квоты** (сброс — раз в сутки по UTC).
  Скрипт готов и воспроизводим: `tools/t11_generation_check.mjs`; результат писать в
  `docs/evidence/raw/t11/`. Прогон нужно повторить один раз и не раньше, чем через сутки.
- Правило на будущее: проверки, которые жгут нейроны, запускать **поштучно и с ограничением сверху**
  (не более N генераций за прогон), а rate-limit проверять на не-генерящем маршруте.
- Урок для отчётов: таймаут клиента ≠ отменённая работа на сервере. Ограничивать нужно количество
  запросов, а не только их длительность.

## D7 · Живые проверки больших тел невозможны с этой машины (подтверждено)

Сводка по D4/D5, теперь с обеих сторон:
- **отправка**: тело запроса >~16 КБ не доходит до Cloudflare (проверено и на `text/plain`);
- **приём**: загрузка больше ~19 КБ обрывается (проверено на `/generate`, где картинка ~250 КБ).

Следствие: локально нельзя ни залить фото в `/classify`, ни скачать сгенерированную картинку.
Всё, что требует больших тел, проверяется только через edge-пробы (маленький JSON в ответе)
или с другой сети. Это ограничение среды разработчика, а не приложения.
