# Журнал решений координатора

Решения, принятые автономно (пользователь был недоступен для ответов). Правило самому себе:
выбирать наименее рискованный обратимый вариант, ничего не тратить и не удалять необратимо,
и оставлять здесь след для финального аудита.

## D1 · Pages-проект создаётся с `--force` (T1)

Новый wrangler делегирует `pages project create` в Workers и без `--force` падает на
«Could not detect a directory containing static files». Создание проекта с `--force` выполнено один
раз; последующие `pages deploy` идут обычным путём, `--force` больше не нужен.
Обратимо: проект можно удалить, приложение — статика.

## D2 · Саб-агенты запускаются через `pi -p`, а не через `claude` (flow-setup)

`claude` CLI установлен, но не залогинен («Not logged in · Please run /login»), а вход требует
интерактивной авторизации, которой в автономном режиме нет. `pi -p --no-session` работает headless,
умеет инструменты и уже авторизован (тот же провайдер, что у сессии). Orca-worktree остаются
доступны, но не потребовались: задачи резались по непересекающимся каталогам.

## D3 · Vision-провайдер требует заголовок `x-opencode-session` (T3)

`https://opencode.ai/zen/go/v1/chat/completions` без заголовка `x-opencode-session` отвечает
400 `MissingSessionID`; с заголовком (значение — любой UUID, провайдер использует его для
маршрутизации диалога) — 200. Проверено вживую: 6.2 с на реальной картинке 1024×1024.
В воркер добавлен `OpenCodeSessionId` на каждый запрос. Так же делает pi (`withOpenCodeSessionHeader`).
ADR-0003 не пересматривается: провайдер тот же, добавлена обязательная деталь протокола.

## D4 · Зависание `/classify` — не дефект воркера, а локальная сеть

Симптом: `POST /classify` с телом ~25 КБ обрывается через ~18–20 с (`curl: (56) Recv failure`).
Разбор:
- `wrangler tail` во время запроса не показал **ни одного события** — запрос не доходит до Cloudflare;
- граница воспроизводится: 4 КБ / 8 КБ / 12 КБ → ответ за 0.07–1.7 с, 16 КБ → таймаут, 20 КБ → обрыв;
- то же самое с `text/plain` без base64 → значит дело в размере тела, а не в содержимом;
- с edge (`tidy-probe2`) `opencode.ai` отвечает 200 за 202 мс, а chat/completions с неверным ключом —
  401 за 509 мс, то есть сеть Cloudflare до провайдера здорова.

Вывод: тело больше ~16 КБ режет **локальная сеть разработчика** — тот же класс проблемы, что описан
в README (Cisco AnyConnect Socket Filter). Это ограничение тестового окружения, а не приложения.
Следствие для проверок: живые проверки с большими телами делать нельзя с этой машины; проверять
через прямые запросы меньшего размера и через edge. Занесено в риск T21.

## D5 · Проверка прод-URL и воркера — через edge, а не из локальной сети (T1, T3)

Локально `*.pages.dev` не проходит TLS (DNS возвращает NXDOMAIN через локальный резолвер, при этом
через DoH записи есть: 172.66.45.7 / 172.66.46.249), а тела >16 КБ теряются. Поэтому живость
проверяется одноразовыми воркерами-пробами на edge Cloudflare (`tidy-probe`, `tidy-probe2`), которые
после проверки удаляются. Ограничение: воркер не может звать другой воркер того же аккаунта
(`error code: 1042`), поэтому проба страниц и проба провайдера — разные пробы.

## D6 · Дневной лимит нейронов Workers AI исчерпан — живой прогон генерации отложен

`POST /generate` начал отвечать 502. Причина найдена через `wrangler tail` (не догадка):

```
[tidy-api] generate model error: 4006: you have used up your daily free allocation of
10,000 neurons, please upgrade to Cloudflare's Workers Paid plan if you would like to continue usage.
```

Это исчерпание бесплатной дневной квоты Workers AI (10 000 нейронов, ADR-0003), а не дефект кода.
Кто израсходовал: живые проверки hardening'а (серия из 25 запросов на rate limit) и, главным образом,
прогон T11 — его retry-цикл слал запросы, каждый из которых **всё равно выполнял генерацию на сервере**,
даже если клиент не дожидался ответа (локальная сеть обрывает загрузку больших тел, D4).

Решения:
- Живой прогон T11 по 8 категориям **отложен до сброса квоты** (сброс — раз в сутки по UTC).
  Скрипт готов и воспроизводим: `tools/t11_generation_check.mjs`; результат писать в
  `docs/evidence/raw/t11/`. Прогон нужно повторить один раз и не раньше, чем через сутки.
- Правило на будущее: проверки, которые жгут нейроны, запускать **поштучно и с ограничением сверху**
  (не более N генераций за прогон), а rate-limit проверять на не-генерящем маршруте.
- Урок для отчётов: таймаут клиента ≠ отменённая работа на сервере. Ограничивать нужно количество
  запросов, а не только их длительность.

## D7 · Живые проверки больших тел невозможны с этой машины (подтверждено)

Сводка по D4/D5, теперь с обеих сторон:
- **отправка**: тело запроса >~16 КБ не доходит до Cloudflare (проверено и на `text/plain`);
- **приём**: загрузка больше ~19 КБ обрывается (проверено на `/generate`, где картинка ~250 КБ).

Следствие: локально нельзя ни залить фото в `/classify`, ни скачать сгенерированную картинку.
Всё, что требует больших тел, проверяется только через edge-пробы (маленький JSON в ответе)
или с другой сети. Это ограничение среды разработчика, а не приложения.

## D8 · Скелетоны — однократное появление вместо бесконечной пульсации (расхождение 10 аудита)

ADR-0005: «Анимации минимальные: 150–200 ms, ease-out, только как отклик на действие. Ничего
декоративного». Факт: скелетоны загрузки бесконечно пульсировали (`animation: pulse … infinite` в
`AddScreen.module.css` и `WardrobeScreen.module.css`). Бесконечный цикл не является откликом на
действие и попадает под прямой запрет ADR-0005.

Решение: бесконечная пульсация убрана полностью. Вместо неё — однократное появление скелетона:
`animation: skeleton-in var(--motion-base) var(--motion-ease)` = **200 ms**,
`cubic-bezier(0.22, 1, 0.36, 1)` (**ease-out**), один проход, без `infinite`. Это отклик на открытие
экрана/начало чтения данных, то есть разрешённый ADR-0005 случай. При `prefers-reduced-motion: reduce`
анимация по-прежнему отключается (`animation: none`).

Исключений нет и не заводится: инвариант закреплён тестом `src/ui/motion.test.ts`, который читает все
CSS-модули под `src/` и падает на любом `infinite` вне явного allowlist (сейчас allowlist пуст). Если
когда-нибудь понадобится осознанное исключение, оно добавляется в allowlist теста **вместе** с пунктом
здесь и точными значениями длительности/итераций.

## D9 · Вырез показывается в сетке и коллаже (снятие противоречия O2 ↔ ADR-0002/T9)

Ревьюер финального ревью нашёл разрыв стыка: `preferredImage` учитывала только роли `ai` и `оригинал`,
поэтому вырез пакшота (`вырез`, T9) не был виден нигде, кроме переключателя в карточке. Для пакшота
массовая оцифровка создавала вырез — и внешне «ничего не происходило».

Решение: порядок предпочтения изображения — **`ai` → `вырез` → `оригинал`**. Обоснование:
- O2 («AI-версия, если есть, иначе Оригинал») ничего не говорит о вырезе — он появился позже, в T9;
- ADR-0002 прямо требует, чтобы пакшот превращался в точный вырез «ради коллажа»: вырез существует
  ровно для того, чтобы вещь выглядела чисто на подложке, и прятать его — обесценивать T9;
- вырез — не AI-версия: пометка об AI в карточке не затрагивается, Оригинал остаётся неизменяемым
  и доступен в карточке.

Следствие: правило «в сетке AI-версия, если есть» сохраняется буквально; вырез подставляется только
там, где AI-версии нет.

## D10 · AI-версия — перерисовка по промпту, а не image-to-image (уточнение ADR-0002 через ADR-0003)

Ревьюер указал: ADR-0002 в «Последствиях» упоминает «image-to-image генерацию», а реализация шлёт
в модель только текст промпта, без пикселей Оригинала.

Разбор требования: ADR-0003 проверен вживую и фиксирует конкретную модель
`@cf/black-forest-labs/flux-1-schnell` — она **text-to-image** (принимает только `prompt` и `steps`,
`additionalProperties: false`). T11 прямо описывает текстовые шаблоны промптов по категориям
(«<вещь>, full garment, front view, centered, plain white background, catalog product photo»).
То есть конкретный способ генерации задан ADR-0003 и T11, а формулировка ADR-0002 описывает смысл
(«перерисовка в каталожный вид»), а не протокол модели.

Решение: оставляем промптовую перерисовку, и **фиксируем ограничение честно**:
- верность вещи обеспечивается промптом (название, цвета, состав) и шаблоном категории, а не пикселями;
- поэтому риск «нарисовало другую вещь» реален и снимается только частично — тем, что Оригинал
  хранится вечно, AI-версия всегда помечена и её можно удалить или перегенерировать;
- переход на image-to-image — отдельное продуктовое решение (другая модель, другой эндпоинт,
  передача Оригинала в воркер). **Требует решения человека**: либо менять ADR-0003 на модель с
  image-условием, либо явно принять текущее ограничение. Сейчас оно принято как известное и
  записано в остаточные риски финального аудита.

## D11 · Альтернативы Workers AI проверены — генерацию закрыть нечем

Пока квота нейронов была исчерпана (D6), проверены все доступные обходные пути, чтобы не ждать сутки:

1. **Прямой повтор `/generate`** на разных ходах (01:25, 01:58, 02:06, 07:00 UTC) — всегда `502`.
2. **Проба AI-binding напрямую** (одноразовый воркер `tidy-ai-probe` с `env.AI.run`,
   после проверки удалён) — точная причина:
   `4006: you have used up your daily free allocation of 10,000 neurons`. Это подтверждает, что дело
   именно в квоте аккаунта, а не в коде воркера, ключе, сети или модели.
3. **Другой провайдер (`opencode-go`)**: эндпоинтов генерации изображений нет
   (`/zen/go/v1/images/generations` и `/image/generations` → 404), а в каталоге из 39 моделей нет ни
   одной image-модели — только чат/vision. То есть vision-провайдер не может подменить генерацию.

Вывод: до сброса суточной квоты Workers AI живой прогон T11 и живое получение AI-версии невозможны.
Скрипт и инструкция готовы (`tools/t11_generation_check.mjs`, `docs/handoff.md`).

## D12 · Генерация переведена на IskraGen (вместо Workers AI)

Причина: бесплатная суточная квота Workers AI исчерпана (D6), а альтернатив внутри Cloudflare нет
(D11). Пользователь выбрал IskraGen: у него минимальное пополнение 100 ₽ (у Zerocoder — 1000 ₽).
Решение принято человеком, это замена части ADR-0003: Pages и воркер остаются на Cloudflare,
генерация — внешний провайдер за воркером.

Факты по провайдеру (сверено с `https://app.iskragen.ru/docs` и публичным каталогом
`GET https://api.iskragen.ru/v1/catalog/`):
- база `https://api.iskragen.ru/v1`, авторизация `Authorization: Bearer isk_live_…`;
- генерация **асинхронная**: `POST /generations` → `202 {id, status, costRub}`; опрос
  `GET /generations/:id`; файл — `GET /generations/:id/download?index=0` (байты, не ссылка);
- выбранная модель `gpt-image-2-text-to-image`: **7 ₽** за кадр 1K, `promptMaxChars = 4000`;
- в каталоге есть дешевле: `nano-banana-2-1` — 4 ₽, `grok-imagine-image-2-0-text-to-image` — 5 ₽;
  slug вынесен в var `ISKRAGEN_MODEL_SLUG`, менять без правки кода;
- неудачная задача (`FAILED`) возвращает деньги автоматически; баланс проверяется
  `GET /v1/billing/balance`;
- лимит провайдера — 5 одновременных генераций, 20 загрузок файлов в минуту.

Как врезано в воркер `tidy-api`:
- клиентский контракт не изменился: `POST /generate {prompt}` → байты картинки одним ответом;
- воркер прячет асинхронность: ставит задачу, опрашивает статус раз в 2.5 с, скачивает файл;
- общий предел ожидания — 75 с (клиент ждёт 90 с), максимум ~32 подзапроса, что укладывается в
  лимит Workers 50;
- коды ошибок: `402` → `billing`, `429` → `rate_limited`, `401/403` → `not_configured`,
  остальное → `502 model_error`; ключ и ответы провайдера наружу не уходят;
- лимит генерации снижен с 20 до 5 запросов/мин на IP: каждый кадр теперь стоит денег;
- ключ живёт только в секрете `ISKRAGEN_API_KEY` и локальном `.dev.vars` (в git не попадает).

Что это **не** решает:
- D10 остаётся: генерация текстовая, по промпту, а не по пикселям Оригинала;
- клиентский токен `VITE_TIDY_CLIENT_TOKEN` по-прежнему вшит в публичный бандл — это барьер от
  сканеров, а не аутентификация. Жёсткий потолок расхода — небольшой баланс на ключе;
- живой прогон ещё не сделан: ждём ключ. Проверять нужно с чистой сети или edge-пробой, потому что
  локальная сеть режет ответы >~19 КБ (D7).

Бюджет проверки: 100 ₽ ≈ 14 кадров `gpt-image-2` (или 25 кадров `nano-banana-2-1`).

## D13 · AI-версия — image-to-image: Оригинал уходит референсом (снимает D10)

Причина: при входе «своё фото» (скрин) vision-модель извлекает только категорию, а
redraw-промпт без цветов и состава рисовал абстрактную вещь категории — пользователь получает
не своё худи. Пользователь решил перейти на image-to-image: провайдер IskraGen это умеет.

Контракт провайдера (сверено с `https://iskragen.ru/docs/api-zagruzka-faylov` и живым
каталогом `GET /v1/catalog/`, 20.10.2026):
- входное изображение подаётся **ссылкой, не base64**: `POST /v1/files/` (multipart, поле
  `file`, ≤ 30 МБ, 20 загрузок/мин, 3 одновременных) → `201 {url, ...}`;
- ссылка подставляется в `params` под ключом из `paramsSchema` модели:
  `input_urls` (Flux 2 Pro, GPT Image 2 / 2.5 Flare), `image_urls` (Grok, Qwen), `image_input`
  (Nano Banana 2/2.1 — принимает до 10–14 референсов);
- i2i-модели IMAGE: `nano-banana-2-1` 4 ₽, `grok-imagine-image-to-image` / `-2-0-image-edit` 5 ₽,
  `flux-2-pro-image-to-image` 6 ₽, `qwen3-image-to-image` / `gpt-image-2-image-to-image` /
  `gpt-image-2-5-flare-image-to-image` 7 ₽. Дефолт i2i — `nano-banana-2-1`.

Как врезано:
- **Воркер `tidy-api`**: `POST /generate` принимает непустой ` prompt` + опционально
  `imageBase64` (data URL или чистый base64) + `mimeType` (jpeg/png/webp/bmp/gif/tiff).
  С картинкой воркер сначала грузит референс в `/v1/files/`, затем создаёт генерацию с
  `params[ключ модели] = [url]`. Потолок декодированных байтов — 8 МБ, тело — 12 МБ
  (`MAX_GENERATE_INPUT_BYTES`/`MAX_GENERATE_BODY_BYTES` в `workers/api/src/config.ts`).
  Сохранённый т2и-выбор с картинкой молча заменяется на i2i-дефолт (лог + честный
  `x-tidy-model`), иначе старые выборы ломали бы весь поток оцифровки.
- **Промпты** (`src/domain/prompt-templates.ts`): новый `buildRedrawPrompt(item)` —
  «redraw the {вещь} from the reference image exactly, keep design/colors/print…», шаблон
  полноты и обязательный хвост кадра. Цвета/состав не перечисляются: их несут пиксели референса.
  `buildGenerationPrompt` остался для текстовых моделей и тестов.
- **Оцифровка** (`src/services/digitize.ts`): дефолтный путь шлёт Оригинал референсом,
  сжав большие фото тем же `canvasResize`, что и распознавание (до 2000 px, JPEG).
  Нечитаемый Blob (jsdom + fake-indexeddb отдают мёртвый клон) — честная деградация в
  текстовую генерацию с `console.warn`, а не сломанная оцифровка.
- Каталог `GET /models` отдаёт 15 IMAGE-моделей; fallback-список клиента синхронизирован.

Что осталось шагом человека: вписать ключ и прогнать живую i2i-генерацию по категориям
(скрипт `tools/t11_generation_check.mjs` следует дополнить референсом); независимо от этого —
наличие таймаут-бюджета на загрузку референса уже покрыто общим дедлайном 95 с.

## D14 · Генерация асинхронная, вход один — фото (ADR-0006)

Причина: живые прогоны после D13 показали, что синхронный `POST /generate` упирается
в дедлайн клиента (95 с) и нестабильную сеть — пользователь получает «Не удалось
связаться с сервисом», хотя воркер и провайдер работают (проверено вживую: 200 за 39 с,
4 ₽). Плюс интерфейс требований: подтверждение со стоимостью перед запуском и понятный
статус.

Решение (полностью в ADR-0006):
1. **Вход один** — «Загрузить фото»; поле ссылки WB удаляется из UI (модули остаются).
2. **Подтверждение**: экран показывает пикер модели и цену из каталога, кнопка «Сделать
   AI-версию · 4 ₽»; генерация только после нажатия.
3. **Асинхронный job**: `POST /generate` → id (202), статус-экран с прогрессом,
   авто-опрос `GET /generations/{id}` каждые ~3 с, кнопка «Обновить» — фолбэк,
   потолок ожидания 5 минут.
4. **Хранение**: после успеха в галерее остаётся только AI-версия, загруженное сырьё
   удаляется — сознательное исключение из правила «Оригинал никогда не удаляется»
   (источником для следующей перегенерации служит сама каталожная AI-версия).

Утверждено владельцем продукта 20.10.2026. Требования: `docs/adr/0006-async-generation-flow.md`,
правки в «Решения» — `docs/tickets.md`.

## D15 · Надёжность async-генерации дописана в ADR-0006; Яндекс отложен, пикер в массовой опущен

Уточнения из разбора ADR-0006 (20.10.2026, по запросу владельца — «всё зафиксировать»):

1. **Идемпотентность и возобновление — часть ADR-0006.** Клиент шлёт `Idempotency-Key`,
   который воркер пробрасывает в IskraGen: повтор `POST` с тем же ключом возвращает
   существующую задачу без повторного списания. `taskId` сохраняется в IndexedDB вместе с
   задачей очереди, поэтому закрытие вкладки после `202` не теряет ни деньги, ни результат:
   при следующем открытии опрос продолжается, готовое забирается кнопкой «Забрать готовое».
   «Повторить» после потолка 5 минут допрашивает статус той же задачи, а не оплачивает заново.
2. **Эндпоинты воркера уточнены**: `POST /generate` → 202 с `taskId`; `GET /generate/{taskId}` →
   JSON-статус; `GET /generate/{taskId}/image` → байты отдельным запросом (файл ~250 КБ не
   должен висеть в теле опроса). Ключ провайдера наружу не уходит.
3. **Опрос только на видимой вкладке** (`visibilitychange`), лимиты воркера: статус 60/мин,
   скачивание 10/мин, параллелизм генераций ≤5 (лимит провайдера из D12).
4. **Исправляется `fetchWithTimeout`**: таймаут снимался после заголовков и не покрывал
   чтение тела — из-за этого скачивание висло без ограничения и клиент получал «Не удалось
   связаться с сервисом» при живом воркере.
5. **Пикер модели и подтверждение стоимости в массовую «Оцифровать всё» не переносятся** —
   опущено по решению владельца. Массовый запуск идёт дефолтной i2i-моделью, цена перед
   запуском не показывается. Известное следствие: бюджет массового запуска не виден,
   а кнопка тратит реальные деньги. Зафиксировано в ADR-0006 («Цена и выбор модели»).
6. **Перенос API на Яндекс-хостинг отложен** по решению владельца. Стек остаётся прежним:
   фронт — GitHub Pages (`https://zakhvatov.github.io/tidy_clone/`), API — Cloudflare Worker
   (`https://tidy-api.megabaff2011.workers.dev`, CORS уже содержит github.io). Вопрос открыт
   в `docs/open-questions.md` (O12), не считается принятым решением навсегда.
7. **Где живёт фронт — записано впервые**: GitHub Pages выбран из-за доступности из РФ
   (проверено ru-узлами, `*.pages.dev` оттуда таймаутил; коммиты `4bfb4b0`, `99262eb` —
   base-aware сборка, workflow, секрет `VITE_TIDY_CLIENT_TOKEN`). Строка «Домен» в
   `docs/tickets.md` приведена в соответствие.
