# T21 — Проверка IPv6 и домена

Проверено 2026-10-14. Сырые данные — `docs/evidence/raw/t21-doh.txt` (DNS-over-HTTPS),
`docs/evidence/raw/t21-local.txt` (локальная картина), `docs/evidence/raw/t21-pages-probe.json`
(edge-проба). Коммиты и деплой — за координатором.

Ссылки: ADR-0003 («Решение: собственный домен с выключенным IPv6»), README
(«Что оказалось ложной тревогой»), `docs/decisions-log.md` D4, D5, D7.

## 1. DNS-факты (DNS-over-HTTPS, `cloudflare-dns.com`)

Локальный резолвер этой сети врёт (D5), поэтому спрашиваем Cloudflare по HTTPS.

| Хост | A | AAAA |
|---|---|---|
| `tidy-clone.pages.dev` | 172.66.45.7, 172.66.46.249 | **2606:4700:310c::ac42:2d07, 2606:4700:310c::ac42:2ef9** |
| `tidy-api.megabaff2011.workers.dev` | 104.21.48.90, 172.67.183.11 | **2606:4700:3032::ac43:b70b, 2606:4700:3037::6815:305a** |

**Вывод по факту №1:** у обоих бесплатных поддоменов Cloudflare (`*.pages.dev` и
`*.workers.dev`) есть AAAA-записи. Это и есть корень проблемы из ADR-0003: клиент видит AAAA,
пробует IPv6, а в сети глобального IPv6 нет — запрос висит вместо быстрого отката на IPv4.

## 2. Локальная картина (воспроизведение)

Из `raw/t21-local.txt`:

- локальный резолвер `192.168.0.1`:
  - `tidy-clone.pages.dev` (A и AAAA) → **NXDOMAIN**;
  - `tidy-api.megabaff2011.workers.dev` → отвечает, и A, и AAAA;
- TLS до `*.pages.dev` не проходит: `curl --resolve tidy-clone.pages.dev:443:172.66.45.7`
  (адрес из DoH) → `Recv failure: Operation timed out` через ~18 с. Это сетевой фильтр
  разработчика (Cisco AnyConnect, D4/D7), а не проблема Pages;
- `*.workers.dev` открывается напрямую: `curl -4 https://tidy-api.megabaff2011.workers.dev/` →
  `http=404`, 0.08 с (404 — норма для корня воркера: он отдаёт только POST-эндпоинты, но TLS и
  маршрут живы);
- IPv6 на машине: `ifconfig` не показывает ни одного глобального IPv6-адреса — только `::1` и
  link-local `fe80::…`. Маршруты по умолчанию для IPv6 ведут в туннели VPN (`utun0…utun3`).
  То есть IPv6 фактически недоступен, хотя AAAA у домена есть — ровно сценарий ADR-0003.

Оговорка: `curl -6` к `workers.dev` вернул `remote_ip=::ffff:172.67.183.11` — это
IPv4-mapped адрес, то есть реально соединение шло по IPv4. Иначе говоря, настоящего IPv6-соединения
не было; подтверждает отсутствие глобального IPv6.

## 3. Доступность извне (edge-проба)

Локально до `*.pages.dev` не добраться (см. выше), поэтому живость проверена одноразовым
edge-воркером `tidy-probe-t21` (как `tidy-probe` в D5). Он дёргал прод-URL и возвращал статусы;
результат — `raw/t21-pages-probe.json`:

| URL | Статус | Тип | Байт | Время |
|---|---|---|---|---|
| `https://tidy-clone.pages.dev/` | 200 | `text/html` | 955 | 93 мс |
| `/manifest.webmanifest` | 200 | `application/manifest+json` | 622 | 6 мс |
| `/sw.js` | 200 | `application/javascript` | 1731 | 157 мс |
| `/apple-touch-icon.png` | 200 | `image/png` | 3188 | 6 мс |

**Воркер-проба удалён** после проверки:
`wrangler delete --name tidy-probe-t21 --force` → `Successfully deleted tidy-probe-t21`;
после удаления тот же URL отвечает `404`, временный каталог `/tmp/tidy-probe-t21` стёрт.

`tidy-api` пробой через воркер не проверялся — воркер не может звать другой воркер того же
аккаунта (ошибка 1042, D5). Для него достаточно прямого запроса из п. 2 (TLS/маршрут жив, 404).

**Вывод по факту №2:** Pages и Worker живы и отдают то, что нужно. Проблема не в деплое, а в
IPv6-откате на клиенте без глобального IPv6.

## 4. Как выключить IPv6-совместимость и когда это сработает

Пошагово (для домена, которым владеете):

1. Добавить домен в Cloudflare (NS-записи указывают на Cloudflare).
2. Cloudflare Dashboard → выбрать **свою зону** → **Network**.
3. **IPv6 compatibility → Off**.
4. Убедиться, что по DoH у домена больше нет AAAA-записей
   (`https://cloudflare-dns.com/dns-query?name=<домен>&type=AAAA` → пусто).
5. Привязать домен как custom domain к Pages-проекту и, при желании, как route к воркеру.

**Когда сработает:** только для зоны, которой вы владеете (купленный домен), потому что тумблер
живёт в настройках зоны.

**Когда НЕ сработает:**

- `tidy-clone.pages.dev` — это зона `pages.dev`, принадлежащая Cloudflare. Ваших настроек зоны у
  неё нет, `Network → IPv6 compatibility` для неё недоступен.
- `tidy-api.megabaff2011.workers.dev` — то же самое: зона `workers.dev` чужая (Cloudflare).
- То есть для бесплатных поддоменов выключить IPv6 **нельзя**. Единственный способ убрать AAAA —
  собственный домен.

## 5. Рекомендация по домену

**Домен сейчас не покупать.** Домен — единственная денежная статья (~200–300 ₽/год), и решает о
деньгах человек, а не исполнитель. До покупки нужно подтвердить сам симптом на реальном устройстве:

- Купить домен имеет смысл, **если** на телефоне жены в её сети приложение открывается медленно или
  зависает, и тест покажет, что причина — предпочтение IPv6 без рабочего IPv6-маршрута.
- **Если** Safari на её телефоне делает быстрый Happy Eyeballs-откат и приложение открывается
  нормально — покупка не нужна, бесплатных поддоменов достаточно.

ADR-0003 не пересматривается: домен остаётся резервным планом, но его включают по факту замера, а не
заранее.

## 6. Что осталось шагом человека (реальный критерий тикета)

- **Замер на телефоне жены в её сети**: открывается ли `https://tidy-clone.pages.dev/` быстро и
  стабильно, нет ли «супер медленно» из-за IPv6-отката. Это и есть критерий готовности T21, и он
  проверяется только на её устройстве и в её сети.
- Если симптом подтвердится — решение о покупке домена и включении `IPv6 compatibility: Off`
  принимает человек.
