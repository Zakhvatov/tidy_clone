## 2. Изображение в сетке — правило D9

В сетке показывается изображение по порядку предпочтения **`ai` → `вырез` →
`оригинал`** (решение D9, `docs/decisions-log.md`; уточняет «Решения» тикета).
AI-версия, если она есть; иначе — точный вырез пакшота (ради коллажа он и
делается, ADR-0002/T9); иначе — Оригинал. Вырез подставляется только тогда,
когда AI-версии нет, поэтому правило «в сетке AI-версия, если она есть»
сохраняется буквально. Раньше вырез в сетку не попадал вообще, и массовая
оцифровка пакшота выглядела для пользователя как «ничего не произошло» —
это был блокер финального ревью, снятый D9.

Изображений нет — карточка показывает только подложку `#F6F6F4`. Пометки об
AI в сетке нет: ни бейджа, ни слова «AI» — тест `в сетке нет слова «AI»`
проверяет это через `queryByText(/ai/i)`; вырез — не AI-версия, пометка об AI
не затрагивается.

## 3. Секции по ADR-0004

Порядок секций берётся из `topCategories()` (= порядок `TAXONOMY`), «Разное»
идёт последней. Внутри секции новые вещи первыми (`датаСоздания` по убыванию,
при равенстве — устойчиво по `id`). Вещь с неизвестной категорией не теряется
и попадает в «Разное». Пустые секции не рисуются.

## 4. Производительность (замер)

Тест `50 вещей: чтение и группировка укладываются в порог` (`fake-indexeddb`)
создаёт 50 вещей с оригиналами, замеряет `loadWardrobe()` и `groupByTopCategory()`
и фиксирует пороги прямо в тесте.

Прогон (живой вывод — `raw/t13-bench.txt`):

```
[T13 perf] loadWardrobe: 0.4 мс, группировка: 0.0 мс, вещей: 50
```

**Честная поправка (расхождение 9 аудита).** Числа выше — один удачный прогон, и
как единственное доказательство они вводят в заблуждение: замер зависит от
прогрева JIT, загрузки машины и того, какие тесты выполнялись до него. Аудитор на
своём прогоне получил `loadWardrobe` **9.4 мс** — то есть на порядок больше, и это
нормальный разброс, а не регрессия. Свой повторный прогон (12× полный файл + 12×
изолированный тест, машина Darwin arm64 / Node v22.22.3; сырые строки —
`raw/t13-bench-rerun.txt`):

| Режим прогона | `loadWardrobe()` | `groupByTopCategory()` |
|---|---|---|
| весь файл `wardrobe.test.ts` (группировка прогрета предыдущими тестами) | 0.4–0.7 мс | 0.0 мс |
| только тест замера (первый вызов — холодный JIT) | 0.7–1.1 мс | 7.2–9.8 мс |
| полный `npm test` (файлы идут параллельно) | 2.3 мс | 0.0 мс |
| независимый прогон (`__independent__/e2e`) | 6.3 мс | 0.1 мс |
| наблюдение аудитора | 9.4 мс | — |

Итого честный диапазон одного и того же кода — примерно **0.4–9.4 мс** в зависимости
от прогрева, параллельной нагрузки и машины. Проверяемое свойство — **порядок
величины, а не абсолют**: и нижняя, и верхняя граница диапазона отличаются от порога
`< 300 мс` на два-три порядка. Порог `< 300 мс`
выбран с большим запасом намеренно: цель — не микробенчмарк, а защита от регрессии
(например, случайного N+1 запроса к IndexedDB), поэтому одиночный «красивый»
результат здесь ничего не доказывает, а устойчивость к 20-кратному разбросу — да.
`loadWardrobe` читает оба стора одной readonly-транзакцией и раскладывает
изображения по вещам одним проходом через `Map`, поэтому сложность —
O(вещи + изображения).

## 5. Ленивая загрузка и память

`ItemImage` рендерит `<img loading="lazy" decoding="async">` и держит
фиксированную пропорцию контейнера 3:4 — вёрстка не прыгает, пока картинка
не пришла. `useObjectUrl` создаёт object URL при появлении/смене `Blob` и
освобождает его при смене и при размонтировании. Тесты (`ItemImage.test.tsx`)
мокают `URL.createObjectURL` / `URL.revokeObjectURL` и проверяют: URL создаётся
один раз, старый освобождается при смене blob, последний — при размонтировании,
при отсутствии blob URL не создаётся вовсе.

## 6. Состояния экрана

- **Загрузка** — скелетоны секций (4 карточки) + текст «Загружаем гардероб…»,
  `role="status"`. Скелетон появляется однократной анимацией 200 ms ease-out
  (ADR-0005, решение D8): бесконечной пульсации нет.
- **Пусто** — «Гардероб пуст» и **сама форма добавления** (`AddItemForm`: поле
  ссылки, «Найти вещь», загрузка фото, превью, «Добавить в гардероб»). Это решение
  O7 («первый экран — поле для ссылки и одна кнопка») и расхождение 11 аудита:
  раньше здесь была только кнопка «Добавить вещь» → `/add`, то есть поля ссылки на
  первом экране не было. После сохранения гардероб перечитывается, и место формы
  занимает сетка. Отдельный экран `/add` (T8) сохранён и использует ту же форму,
  поэтому логика добавления не дублируется.
- **Ошибка чтения** — `ErrorNotice` с текстом «Не удалось прочитать гардероб.
  Попробуйте ещё раз» и кнопкой «Повторить», которая перезапускает чтение без
  перезагрузки страницы.

## 7. Тесты

`src/services/wardrobe.test.ts` (6):
- `loadWardrobe` отдаёт вещи вместе с их изображениями;
- `preferredImage`: порядок `ai` → `вырез` → `оригинал` (D9), самая новая
  AI-версия/вырез, только Оригинал, пустой список → `undefined`, чужое
  изображение не подставляется;
- порядок секций ADR-0004, «Разное» последней, неизвестная категория в «Разное»;
- сортировка внутри секции — новые первыми;
- 50 вещей: пороги чтения и группировки.

`src/app/screens/WardrobeScreen.test.tsx` (14):
- пустой гардероб → на `/` сама форма добавления (O7), добавление по ссылке кладёт
  вещь в сетку, поле ссылки исчезает с появлением вещей;
- непустой гардероб → на `/` нет поля ссылки, есть сетка;
- 50 вещей → 8+1 секция, счётчики верны, порядок по ADR-0004;
- вещь с AI-версией показывает AI, без неё — Оригинал (проверен `src` картинки);
- пакшот с вырезом и без AI показывает вырез, а при наличии AI — AI (D9);
- в сетке нет слова «AI»;
- внутри секции новые первыми;
- ошибка чтения → понятное сообщение и «Повторить» возвращает сетку.

`src/ui/ItemImage.test.tsx` (4): `loading/decoding`, отсутствие blob, освобождение
URL при размонтировании и при смене blob.

`src/ui/motion.test.ts` (1): читает CSS-модули под `src/` и падает на любом
`infinite` вне явного allowlist. Пустой allowlist — инвариант ADR-0005/D8:
бесконечных анимаций нет нигде.

## 9. Не сделано / риски

- **Карточка вещи (T15) не делалась**: клик по карточке ведёт на `/` (заглушка
  по условию тикета). Переключение Оригинал/AI, перегенерация и удаление — T15.
- **Фильтры и поиск (T14), редактор образов (T16+)** не делались.
- Замер снят на `fake-indexeddb` в jsdom, а не на реальном IndexedDB Safari:
  это проверка сложности и защита от регрессии, а не абсолютное время на iPhone.
  Реальные изображения по 100–300 КБ добавляют время декодирования, но оно ленивое
  и не блокирует показ сетки.
- `loading="lazy"` не грузит картинки за пределами вьюпорта; в jsdom это не
  проверяется поведенчески — тест фиксирует сами атрибуты.

## 10. Спорные решения

| Решение | Почему так |
|---|---|
| Правило изображения вынесено в `preferredImage(вещь, изображения)` из сервиса | Правило из «Решений» (уточнённое D9) — доменное, а не разметки: его переиспользуют сетка, коллаж T16, редактор, пикер и список образов. Параметр `вещь` нужен, чтобы не подставить изображение чужой вещи защитно. |
| Object URL живёт в UI-хуке, а не в сервисе | `URL.createObjectURL` — браузерный ресурс со временем жизни компонента; сервис не должен знать о React и размонтировании. |
| Правка `src/app/routing.test.tsx` | Экран `/` теперь читает IndexedDB асинхронно, поэтому проверка «Гардероб пуст» стала асинхронной (`findByText`), а в тест добавлен `fake-indexeddb`. Без этой правки старый тест падал бы на скелетоне. |
| `ItemImage` — новый компонент, а не правка `PhotoPreview` | `PhotoPreview` чужой и не умеет `loading="lazy"`; сетке нужны ленивая загрузка и освобождение URL на много карточек. `PhotoPreview` оставлен как есть. |
| Вещи с неизвестной верхней категорией уходят в «Разное» | Данные-строки таксономии редактируемы (T15), поэтому сетка не должна терять вещь с «чужой» категорией. |
