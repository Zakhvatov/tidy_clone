## 2. Формат файла (версионируется)

Один JSON-документ, без ZIP и без внешних зависимостей. Изображения (Оригиналы, AI-версии,
вырезы) — строками base64; рядом лежит `размер` исходных байтов, поэтому битый base64 ловится
до записи в IndexedDB. Полный пример — `docs/evidence/raw/t19-backup-example.json`:

```json
{
  "format": "tidy-clone-wardrobe",
  "formatVersion": 1,
  "createdAt": "2026-10-14T12:00:00.000Z",
  "вещи": [ { "id": "…", "название": "Худи", "idИзображений": ["…"] } ],
  "изображения": [
    { "id": "…", "idВещи": "…", "роль": "оригинал", "размер": 8, "base64": "iVBORw0KGgo=" }
  ],
  "образы": [ { "id": "…", "элементы": [ { "idВещи": "…", "позиция": { "x": 0, "y": 0 } } ] } ]
}
```

Осознанный размен: JSON+base64 примерно на треть больше суммы картинок, зато файл читается
любым редактором и не тянет в проект библиотеку распаковки. Скачивание — `Blob` +
`URL.createObjectURL`, без сети и без облака; имя файла `wardrobe-backup-ГГГГ-ММ-ДД.json`.

`formatVersion` и таблица миграций (`МИГРАЦИИ` в `backup.ts`) — задел под старые форматы:
неизвестная версия не ломает хранилище, а даёт понятный текст («Файл создан более новой
версией приложения (формат N). Обновите приложение…»).

## 3. Импорт: слияние без потерь

Поведение при совпадении id — **объединение, ничего не удаляется**:

- **Вещь**: если в базе новее (`датаОбновления`), она остаётся, входящая пропускается; иначе
  вещь обновляется. Так импорт старой копии не затирает свежие правки.
- **Изображение**: при занятом id сначала сравниваются байты. Совпали — не дублируем. Отличаются
  — сохраняем копию с новым id, а ссылку в вещи переставляем на неё: Оригинал из базы не
  перезаписывается (ADR-0002) и ни один байт не теряется.
- **Образ**: при совпадении id остаётся тот, что уже в базе (у образа нет `датаОбновления`,
  сравнить «свежесть» нельзя).

Перед записью экран делает `prepareImport` — проверяет файл и показывает план («будет
добавлено / обновлено / пропущено»), и только после подтверждения `applyImport` пишет одной
транзакцией на `items`, `images`, `outfits`. Ошибка на середине откатывает всё: гардероб
остаётся прежним. Результат импорта показывается счётчиками.

## 4. Офлайн

- Данные и так локальные, все экраны открываются без сети — проверено тестом
  `src/app/offline.test.tsx` для `/`, `/add`, `/outfits`, `/backup` при `navigator.onLine === false`.
- Там, где сеть нужна (импорт по ссылке WB на `/add`, распознавание фото, оцифровка в
  `DigitizePanel`), при отсутствии сети показывается `OfflineNotice`: «Нет сети. Это действие
  требует интернета…». Загадочной ошибки запроса пользователь не видит.
- Service worker: конфиг вынесен в `src/app/pwa.ts` и покрыт `src/app/pwa.test.ts`
  (`navigateFallback: '/index.html'`, прекеш `js/css/html/png/svg/webmanifest`,
  `cleanupOutdatedCaches`, `skipWaiting`, `clientsClaim`).
- Собранный `dist/sw.js` содержит `createHandlerBoundToURL("/index.html")` и прекеш
  `index.html`, `assets/index-*.js`, `assets/index-*.css` — оболочка SPA отдаётся офлайн
  (сырое доказательство — `docs/evidence/raw/t19-preview.txt`).
- `npm run build && npm run preview`: маршруты `/`, `/add`, `/outfits`, `/backup` отдают
  index.html (200), `/sw.js` и `/manifest.webmanifest` — 200.

**Честно:** браузера в среде нет, реальный офлайн-прогон в Safari/Chrome вручную не выполнен.
Доказательство офлайна — конфиг + содержимое собранного `sw.js` + ответ preview на глубокий
маршрут, а не живой полёт в самолётном режиме.

## 6. Что проверяют тесты T19

- экспорт пустого гардероба → валидный файл (счётчики 0, документ разбирается);
- имя файла содержит дату;
- экспорт ничего не теряет: счётчики вещей/изображений/образов совпадают с гардеробом;
- экспорт → импорт в пустую базу восстанавливает вещи, изображения (сравниваются байты и
  размеры) и образы;
- повторный импорт того же файла не создаёт дубликатов (идемпотентность);
- импорт поверх существующего гардероба не теряет данные (более новая вещь и второй образ
  остаются);
- вещь из файла новее — обновляется;
- занятый id изображения с другими байтами → копия с новым id, оригинал цел, ссылка переставлена;
- не JSON → `not_json`; чужой JSON → `not_backup`; неизвестная версия → `version`; битый base64
  и несовпадение `размер` → `corrupt`; битая ссылка на изображение → `corrupt`; после каждой
  ошибки база не тронута;
- `prepareImport` показывает план и не пишет;
- экран: доступен из навигации, экспорт скачивает файл и сообщает итог, импорт показывает план,
  после подтверждения восстанавливает данные, битый файл и файл новой версии дают понятные ошибки.

## 7. Риски и границы

- `src/app/App.tsx` и `src/app/AppLayout.tsx` правятся параллельно исполнителем T16–T18
  (добавлен роут `outfit/:id`). Правки не пересекаются по строкам, но при слиянии веток
  возможен конфликт — координатору проверить итоговый файл.
- Формат хранит base64 в памяти при экспорте/импорте: для гардероба в сотни мегабайт это
  заметная нагрузка. Для личного масштаба (десятки вещей) приемлемо; ZIP/потоковая запись —
  отдельная задача, если объём вырастет.
- `fake-indexeddb` не клонирует jsdom-`Blob`, поэтому тесты T19 подменяют глобальный `Blob` на
  `node:buffer` внутри своего файла. Это тестовая деталь, кода приложения не касается.

## 8. Подложка образа в копию не входит (осознанно)

Подложка образа хранится в `localStorage` под ключом `tidy.outfit.background.<id>`
(`src/services/outfit-background.ts`), а не в самом **Образе** (`src/domain/types.ts`): поля
под неё в домене нет. Поэтому резервная копия (вещи, изображения, образы) её **не включает** —
это осознанный размен, а не пропуск: при восстановлении на новом устройстве подложки вернутся
к белой, а сам образ и его композиция не пострадают.

**Обновлено fix-review.** Утечка ключей закрыта: при удалении образа его ключ подложки удаляется
(`удалитьФон`, вызов из `OutfitsScreen`), отдельный тест `outfit-background.test.ts` и тест экрана
списка образов это закрепляют. Переносить подложку в доменный `Образ` через миграцию схемы
**не стали**: это меняло бы формат резервной копии (`formatVersion`) и домен ради настройки
отображения — цену не оправдывает.
